# Шина ESP32-S3 ↔ ПЛИС: протокол golden

## Физика
- **Шина:** quad SPI, режим 0, ESP — master, half-duplex. Каждый кадр: CS# в 0, команда 8 бит и адрес 24 бита по 4 линиям (8 тактов SCK). Дальше одно из двух:
  - запись: данные от ESP;
  - чтение: 8 dummy-тактов, затем данные от ПЛИС.
- **Порядок бит:** старший нибл первым, бит 7 на IO3.
- **Приём в ПЛИС:** оверсемплинг на 100 МГц, поэтому SCK не выше ~12 МГц. На 80 МГц нужен source-synchronous приёмник (этап после макета).
- **IRQ:** 1, когда golden свободен (не занят флешем или ICAP). У ESP вход с подтяжкой к 0, поэтому выключенная или несконфигурированная ПЛИС читается как «занят».

| Сигнал | ESP32-S3 | ПЛИС i9+ | Гребёнка P3 девборды i5/i9 |
|---|---|---|---|
| SCK | GPIO12 | Y18 (MRCC, банк 14) | 7 (подпись i5: C4) |
| CS# | GPIO10 | W19 (подтяжка вверх) | 9 (C3) |
| IO0 (D) | GPIO11 | Y19 | 12 (A3) |
| IO1 (Q) | GPIO13 | V18 | 13 (B1) |
| IO2 (WP) | GPIO14 | V19 | 17 (C1) |
| IO3 (HD) | GPIO9 | AA20 | 16 (D1) |
| IRQ | **GPIO5** | AA21 | 15 (E2) |
| GND | GND | | 11, 8, 2, 20, 29 |

GPIO46 под IRQ не годится: это стрэпинг-пин. Если ПЛИС держит на нём 1, ESP не входит в режим загрузки прошивки (GPIO0=0 требует GPIO46=0). Для материнки вывод тот же.

## Команды
Номера в коде: `gateware/common/golden_core.sv` (golden), `gateware/common/profile_shell.sv` (профиль), `firmware/ports/esp32s3/components/fpga_link/include/fpga_link.h`.

| Код | Имя | Фаза | Что делает |
|---|---|---|---|
| 01 | ID | чтение 8 | `"FBGL"`, версия, режим (0 golden, 1 профиль), id профиля (2 байта) |
| 02 | STATUS | чтение 8 | [0] бит 0 busy, бит 1 ошибка, бит 2 идёт заливка плоскости, бит 3 на экране плоскость; [1] код ошибки; [2..5] BOOTSTS (BE); [6..7] счётчик кадров видео (BE) |
| 03 | BUF_W | запись ≤8192 | в буфер 8 КБ с адреса `addr[12:0]` |
| 04 | BUF_R | чтение ≤8192 | из буфера |
| 05 | PARAM | запись 8 | len (BE32, ≤ 16 МБ), buf_off (BE32, < 8192) |
| 06 | RESULT | чтение 4 | результат последней операции флеша (CRC, ID, SR) |
| 07 | TUNE | запись 4 (ключ) | `addr[7:0]` передних фронтов SCK до первого нибла, `addr[8]` менять данные по заднему фронту |
| 08 | LA_ARM | запись 4 (ключ) | отладка: захватить следующий кадр анализатором |
| 10 | ERASE64K | — | стереть 64 КБ по `addr` (кратно 0x10000, не ниже 0x400000) |
| 11 | PROG | — | записать len байт из буфера (buf_off) с `addr`, не ниже 0x400000 |
| 12 | READ | — | прочитать len байт с `addr` в буфер (buf_off) |
| 13 | CRC | — | CRC-32 (IEEE) len байт с `addr`, результат в RESULT |
| 14 | FL_ID | — | JEDEC ID флеша в RESULT |
| 15 | FL_SR | — | регистр статуса флеша в RESULT |
| 20 | BOOT | — | WBSTAR = `addr`, IPROG (ICAP) |
| 22 | REBOOT_GOLDEN | запись 4 (ключ) | профиль: IPROG на 0 (нужен ICAP, см. ниже) |
| 30 | CSR_W | запись 4·n | профиль: регистры с индекса `addr[7:0]`, слова старшим байтом вперёд |
| 31 | CSR_R | чтение 4·n | профиль: то же на чтение |
| 32 | STREAM | запись n | профиль: байты в поток канала `addr[7:0]`; обратного давления нет, свободное место ESP читает из регистра профиля |

| 33 | PAD | запись 4 | профиль: кнопки {пад 1, пад 0} по 16 бит, BE; слово принимается целиком по CS#↑ и только при ровно 4 байтах |
| 34 | CAPTURE_R | чтение n | профиль с `Readback`: замороженный захват с байтового адреса `addr`, без изменения курсора; недоступные байты равны 0 |
| 40 | OSD_RECT | запись ≤8192 | golden: прямоугольник в плоскость меню, см. «Плоскость меню» |
| 41 | OSD_FILL | запись 5 | golden: заливка прямоугольника |
| 42 | OSD_PAL | запись 3·n | golden: палитра с индекса `addr[3:0]`, RGB888 |
| 43 | OSD_CTRL | запись 4 (ключ) | golden: `addr[0]` = 1 показывать плоскость, 0 заставку |

Профиль отвечает на 01 (`"FBPR"`), 07, 22, 30–34. Значение регистров задаёт сам профиль. Команда 34 без `Readback` возвращает нули.

## Профиль ЛА на стенде

`gateware/profiles/la/la_top.sv`, ID профиля `0x4C41`. Сборка: `make -C gateware viv_la_top`.
Входы P2 работают как LVCMOS33, без входной защиты и регулируемого порога. Прямое подключение 5 В запрещено.
Цель сборки по умолчанию: 16 каналов, 100 MS/s. Сборка `make -C gateware viv_la_top LA_DDR=1`
включает IDDR на обоих фронтах такта 100 МГц: номинально 200 MS/s, шаг 5 нс.
`make -C gateware viv_la_top LA_SERDES=1` включает ISERDESE2 DDR 1:4: номинально 400 MS/s,
шаг 2,5 нс. CLK=200 МГц и CLKDIV=100 МГц идут от одного PLL через BUFG, без асинхронной
границы между входным кадром и памятью. `LA_SERDES=1` имеет приоритет над `LA_DDR`.
Входную полосу, достоверность захвата и минимальную ширину импульса на проводах нужно измерить.
Все три сборки используют 64 RAMB36. SDR хранит 131 072 отсчёта по 16 бит: 1,31072 мс при 100 MS/s.
DDR хранит до 131 070 отсчётов: 655,35 мкс при 200 MS/s. Одна пара в кольце зарезервирована,
чтобы последняя полная запись не затёрла начало окна с нечётным адресом.
ISERDES хранит 131 068 отсчётов: 327,67 мкс при 400 MS/s; резерв составляет четыре отсчёта.
Входной режим выбирается при сборке, не через CSR. Сборки пишут один путь `build/vivado/la_top.bit`;
последняя сборка заменяет предыдущий артефакт. Фактическую конфигурацию сообщают CAPACITY и BASE_HZ.

Номера ниже — индексы 32-битных регистров, не байтовые адреса. Шина передаёт слова CSR в BE.

| Индекс | Регистр | Значение |
|---|---|---|
| 0 | ID | `FBLA` |
| 1 | CTRL | `0x4C410001` ARM, `0x4C410002` ABORT; другие ключи не действуют |
| 2 | STATUS | бит 0 busy, 1 triggered, 2 done, 3 bad_config |
| 3 | CAPACITY | максимальное число отсчётов |
| 4 | BASE_HZ | номинально 100 000 000 / 200 000 000 / 400 000 000 Гц, без калибровки генератора |
| 5 | TOTAL | длина окна, 1…CAPACITY |
| 6 | POST | число отсчётов от триггера включительно, 1…TOTAL |
| 7 | DIVIDER | частота BASE_HZ / (DIVIDER + 1) |
| 8, 9 | MASK, VALUE | условие `(sample & MASK) == (VALUE & MASK)` |
| 10, 11 | RISE, FALL | обязательные фронты на выбранных битах; бит не может входить в обе маски |
| 12 | COUNT | число действительных отсчётов после done; иначе 0 |
| 13 | TRIGGER_INDEX | позиция триггера в окне, начиная с 0 |
| 14 | EPOCH | счётчик ARM; хост сверяет до и после выгрузки |
| 15 | CAPTURE_DIVIDER | делитель, сохранённый при ARM |
| 16 | SOURCE | 0 входы P2, 1 внутренний 16-битный счётчик выбранных отсчётов |
| 17 | CAPTURE_SOURCE | источник, сохранённый при ARM |

ARM сохраняет настройки и заменяет прошлый захват. До разрешения триггера кольцо накапливает
TOTAL − POST отсчётов. Условия MASK/VALUE, RISE и FALL действуют совместно. Нулевые маски дают
безусловный триггер после предзапуска. ABORT инвалидирует данные; повторный ARM начинает новый захват.
Запись настроек во время захвата меняет только следующий ARM.
В DDR lane 0 содержит отсчёт переднего фронта, lane 1 следующего заднего фронта
(`IDDR SAME_EDGE_PIPELINED`, [UG471, с. 109–112](https://docs.amd.com/v/u/en-US/ug471_7Series_SelectIO)).
Триггер проверяет отсчёты в этом порядке. Прореживание считает отдельные полутакты и упаковывает
выбранные отсчёты в кадры; DIVIDER=2 в DDR даёт равномерный шаг 15 нс.
В ISERDES Q4, Q3, Q2, Q1 соответствуют lane 0…3 от старейшего к новейшему; BITSLIP выключен.
DIVIDER=2 в этом режиме даёт равномерный шаг 7,5 нс, независимо от границ четырёхотсчётных кадров.
Данные после сброса недействительны до завершения прогрева входного конвейера.

После done команда 34 читает окно от старейшего отсчёта. Формат: отсчёты по времени, LE16, D0 в бите 0.
Адрес и длина могут быть нечётными; чтение за COUNT × 2 возвращает нули. Повторное чтение не меняет данные.
Для выгрузки хост удерживает владение захватом: не отправляет ARM/ABORT и проверяет EPOCH и done после чтения.
IRQ сохраняет смысл «шина профиля готова», а не «захват закончен»; готовность захвата читается из STATUS.

| Каналы | Контакты P2 | Шары ПЛИС |
|---|---|---|
| D0…D7 | 4, 5, 6, 7, 9, 12, 13, 15 | U2, V2, W1, AA1, W2, AB2, AB3, Y6 |
| D8…D15 | 17, 18, 19, 22, 24, 25, 26, 28 | Y3, AA3, Y2, AB1, Y1, V3, U3, R2 |

P2-3/14/16/27 профиль не использует. Шина ESP остаётся на P3. Назначение шаров:
[Colorlight i9+](https://github.com/wuxx/Colorlight-FPGA-Projects/blob/master/colorlight_i9plus_v6.1.md),
таблица SO-DIMM; контакты P2 соответствуют схеме девборды i5/i9.
Симуляция: `make -C gateware sim_la_ring sim_la`.
Проверка IDDR использует установленную модель AMD UNISIM, без копирования её исходников в репозиторий:

```bash
# XILINX_VIVADO задаётся окружением Vivado; вместо него можно передать UNISIM=<каталог модели>.
make -C gateware sim_la_sampler sim_la_ddr sim_la_ddr_qspi \
  UNISIM="$XILINX_VIVADO/data/verilog/src"
```

ISERDESE2 использует AMD SecureIP, поэтому его тесты запускаются в Vivado Simulator:

```bash
make -C gateware sim_la_serdes sim_la_serdes_qspi
```

Исходники модели не копируются в репозиторий. Для линковки симулятора может потребоваться
`LIBRARY_PATH` с системным каталогом библиотек C; его задаёт окружение сборки.
Тесты проверяют PRBS на 16 входах, хронологию фаз, reset/startup, прореживание с шагом 1…18,
триггер на каждой позиции кадра, кольцевое окно и чтение через QSPI. Прохождение модели и STA
подтверждает цифровую реализацию; оно не заменяет испытания асинхронных входов и щупов.
Асинхронная граница P2 → ISERDES намеренно исключена из setup/hold анализа. `report_cdc`
отмечает её как critical: это не доказательство когерентности внешней шины или отсутствия
метастабильности. Внутренние пути после сэмплера остаются под анализом таймингов.

### ESP и выгрузка в PulseView

Команда `capture` использует текущую USB-Serial-JTAG консоль ESP32-S3. Команда `la` остаётся
отладчиком шины golden. Профиль ЛА должен быть загружен отдельно; команда `capture` не меняет профиль.

```text
capture arm total post divider [mask value rise fall source]
capture status
capture read epoch offset bytes
capture abort
```

`source=0` выбирает входы P2, `source=1` внутренний счётчик. Неуказанные маски и источник равны 0.
Числа принимаются в десятичной записи или с префиксом `0x`. `read` возвращает 1…1024 байта.
Каждая команда выдаёт одну строку `@LA {JSON}`. Ответ `status` содержит flags, capacity, base_hz,
count, trigger_index, epoch, divider и source. Ответ `read`: op=`data`, epoch, offset,
hex и CRC32 IEEE этих байтов. Ошибка: ok=`false`, error, message, detail.
CRC32 проверяет передачу ESP → ПК; он не подтверждает целостность выборок на входе ПЛИС или на QSPI.

Клиент ESP удерживает замок шины только на проверке состояния и чтении блока. Между блоками кнопки
и лаунчер продолжают работать. Смена профиля, ARM или ABORT во время выгрузки отменяет результат.
Хост проверяет длину и CRC32 каждого блока, затем повторно читает метаданные захвата.

```bash
# После загрузки профиля: 16 каналов, номинально 100 MS/s, окно 131072 отсчёта
uv run --with pyserial python host/tools/la_capture.py capture.sr \
  --port /dev/ttyACM1 --arm --samples 131072 --post 65536

# Проверка тракта внутренним счётчиком: 25 MS/s, триггер на значение 5000
uv run --with pyserial python host/tools/la_capture.py counter.sr \
  --port /dev/ttyACM1 --arm --samples 2048 --post 1024 --divider 3 \
  --mask 0xffff --value 5000 --source 1

# Выгрузка уже завершённого захвата без ARM
uv run --with pyserial python host/tools/la_capture.py capture.bin --port /dev/ttyACM1

# Максимальное окно загруженного профиля; ёмкость берётся из CAPACITY
uv run --with pyserial python host/tools/la_capture.py capture.sr --port /dev/ttyACM1 --arm
```

Имя порта выбирает пользователь. Открытие USB-Serial-JTAG может перезапустить ESP; утилита ждёт
приглашения консоли. ПЛИС сохраняет захват до следующего ARM/ABORT, сброса или смены профиля.
Не открывайте одну консоль одновременно несколькими программами.

Для `.sr` нужен `sigrok-cli`. Утилита сохраняет частоту без округления: если BASE_HZ / (DIVIDER + 1)
не целое число Гц, используйте `.bin`. Рядом с каждым файлом создаётся `<имя>.json`: точное отношение
частот, позиция триггера, источник, EPOCH и CRC32 полного RAW-захвата. Частота номинальная, без
калибровки генератора. Позиция триггера хранится в JSON; конвертер binary не переносит её в PulseView.
Утилита не перезаписывает существующие файлы и публикует данные только после проверки захвата.
Передача через текстовую консоль удваивает объём данных из-за hex; это диагностический транспорт,
а не потоковый USB-драйвер ЛА.

Без железа: `--log console.log` вместо `--port` читает готовую последовательность строк `@LA`.
Проверки клиента и консоли: `make -C firmware/tests test`; хоста: `python3 -m unittest discover -s host/tests -v`.

### Экран ЛА по HDMI

Профиль ЛА выводит 640×480 через существующий HDMI-тракт. Монохромная плоскость занимает
10 RAMB36 рядом с 64 RAMB36 захвата; глубина захвата не меняется. Супервизор использует тот же
UI и шрифты, что меню golden, и преобразует четыре бита яркости в один бит с растровым порогом.
Golden сохраняет прежнюю плоскость с палитрой.

| Команда/CSR | Назначение |
|---|---|
| `0x44 MONO_RECT` | Адрес `{y[11:0], x[11:0]}`; `w(2), h(2)` BE, затем строки по `w/8` байтов; старший бит левее |
| `0x43 OSD_CTRL` | Ровно четыре байта `FBKY`; адрес 1 включает плоскость, 0 гасит |
| CSR 64 | `FBMV` (`0x46424D56`): наличие монохромной плоскости |
| CSR 65 | Бит 0: показ включён |

Для `MONO_RECT` x и w кратны 8. Нулевую ширину, некратные координаты/ширину и пиксели за экраном
профиль отбрасывает; координаты не оборачиваются. После сброса показ выключен, содержимое RAM
не задано: перед включением супервизор передаёт полный кадр. Передача не двойная, поэтому при
обновлении возможен разрыв кадра. Флаг показа проходит через двухступенчатый синхронизатор;
исключение тайминга ограничено его первым триггером. Второй триггер и тракт захвата остаются timed.

Лаунчер запускает файл `la` с карточки ЛА. Перед входом экран проверяет ID профиля и CSR 64;
старый профиль без видеоплоскости через консоль по-прежнему поддерживает `capture`.
Кнопки стенда: A/F2 или Меню запускают захват, повторное нажатие при ожидании останавливает его;
▲▼ выбирают канал, B/F3 меняет триггер `* / ▲ / ▼`, X/F1 приближает, Y/F4 отдаляет,
◀▶ сдвигают окно на четверть его длины. `*` означает отсутствие условия триггера;
▲ и ▼ означают передний и задний фронты выбранного канала.

Захват с экрана: все 16 входов P2, полная доступная ёмкость, половина окна после триггера,
номинально 10 MS/s. Остальные настройки доступны через консоль `capture arm`.
Экран не запускает повторный захват сам и не включает тестовый генератор.
Для расширенного окна он сохраняет первое/последнее значение, AND и OR каждого столбца:
короткий импульс остаётся видимым при уменьшении масштаба, но его точное положение внутри
столбца неизвестно. Числа над дорожками задают полуоткрытый интервал индексов отсчётов.

Завершённый захват остаётся в ПЛИС, прокрутка и масштаб не меняют EPOCH. Для выгрузки текущего
захвата используйте `la_capture.py capture.sr --port <порт>` без `--arm`; новая кнопка захвата
во время выгрузки приведёт к отказу проверки EPOCH. Ускорение USB и потоковый режим сюда не входят.
Выход Fn+Назад сохраняет прежний возврат в golden. При подключённой тестовой петле сначала
отключите оба USB и снимите перемычки перед сменой профиля.

Проверки: `make -C gateware sim_la_plane`, `make -C firmware/tests test`.

### Внешняя тестовая петля P6 → P2

Сборка `make -C gateware viv_la_top LA_SERDES=1 LA_LOOPBACK=1` добавляет восемь выходов
генератора на свободные контакты P6 банка 35. По умолчанию `LA_LOOPBACK=0`: генератора нет,
выводы находятся в Hi-Z. В тестовой сборке после конфигурации и сброса выходы тоже в Hi-Z;
включение требует ключа. Профиль не подключает генератор к захвату внутри ПЛИС: сигнал проходит
через выходную площадку, провод, вход P2 и сэмплер.

Внешний монтаж выполняют **при выключенном питании стенда**. Первые восемь перемычек:

| Выход | P6, контакт | Шар | P2, контакт | Канал |
|---|---:|---|---:|---|
| T0 | 3 | L4 | 4 | D0 |
| T1 | 4 | G4 | 5 | D1 |
| T2 | 5 | G3 | 6 | D2 |
| T3 | 6 | K2 | 7 | D3 |
| T4 | 7 | M1 | 9 | D4 |
| T5 | 9 | K1 | 12 | D5 |
| T6 | 12 | H3 | 13 | D6 |
| T7 | 22 | J1 | 15 | D7 |

Для второй группы те же T0…T7 переставляют на P2-17/18/19/22/24/25/26/28, то есть D8…D15.
Генератор перед перестановкой выключают; затем отключают питание. После включения сначала
проверяют статические коды. Нумерацию контактов сверяют с первым контактом разъёма на плате,
а не отсчитывают от произвольно выбранного края. Контакты SO-DIMM и P6 сверены по таблице i9+
и схеме девборды i5/i9.

P2 и P6 уже имеют общую землю через плату. Короткие дополнительные провода P6-2 → P2-2 и
P6-20 → P2-20 уменьшают петлю возвратного тока. Землю внешнего анализатора подключают к GND.
Выводы питания **1/10/21/23/30 обоих разъёмов не используют**. В частности, контакт 23 — 5 В.
В петле только логика 3,3 В. К P6 не подключают выходы другого устройства.

Последовательные резисторы 100–220 Ом рекомендуются для ограничения тока при ошибках монтажа.
Без них прямую петлю используют только после сверки направления: P6 — выходы этого генератора,
P2 — входы ЛА. `DRIVE 4`, `SLEW SLOW` задают слабый драйвер и плавные фронты, но **не являются
защитой от короткого замыкания или 5 В**. Низкая частота не исключает звон на длинных проводах.
Пока петля соединена, другие профили и golden не загружают: их направления выводов могут отличаться.

Регистры генератора доступны через существующую команду ESP `csr`:

| Индекс | Назначение |
|---|---|
| 32 | CTRL: старшие 16 бит `0x4C47`, бит 0 включение, биты 2:1 режим |
| 33 | PERIOD: число тактов 100 МГц на состояние; значения меньше 100 ограничиваются до 100 |
| 34 | VALUE: статический байт или seed PRBS; нулевой seed заменяется на `0xA5` |
| 35 | ID: `FBLG` (`0x46424C47`), только при наличии генератора |

Режимы: 0 статический VALUE, 1 счётчик 0…255, 2 бегущая единица, затем бегущий ноль,
3 PRBS с периодом 255 состояний. Запись PERIOD/VALUE меняет настройки следующего включения;
запись CTRL с ключом сохраняет их и перезапускает последовательность. Максимальная скорость
смены состояний — 1 Мсостояние/с, без режима быстрых импульсов.

```text
csr 35                    # проверить FBLG
csr 32 0x4c470000          # выключить выходы
csr 34 1
csr 32 0x4c470001          # статический T0=1, остальные 0
csr 32 0x4c470000          # выключить перед изменением проводки
```

Статическими значениями 1/2/4/8/16/32/64/128 и их побитовыми инверсиями проверяют проводку.
Затем используют счётчик или PRBS, например PERIOD=1000 для 100 ксостояний/с. Это позволяет
сравнить медленные сигналы с внешним анализатором 24 MS/s. Генератор и сэмплер используют общую
опору: такая петля не подтверждает абсолютную точность времени или предельную входную полосу.
UART/SPI и независимый источник в эту первую тестовую сборку не входят.

Симуляция: `make -C gateware sim_la_loopback`; с AMD SecureIP:
`make -C gateware sim_la_loopback_serdes`. Тест включает внешние провода с задержкой,
без обхода сэмплера, и проверяет обе группы по восемь входов. Это функциональная модель,
а не модель электрического качества проводов.

## Плоскость меню (golden, версия 2)
Golden выводит HDMI 640×480 60 Гц. Меню рисует супервизор в плоскость 640×480 по 4 бита на пиксель с палитрой 16 × RGB888 (`gateware/common/video/osd_plane.sv`, 38 RAMB36). Пока супервизор не включил плоскость командой 43, на экране заставка: логотип Fabbit 400×95 пикселей в (120, 182), как `boot-640x480` бренд-кита.

- **Адрес** в 40 и 41: `addr = {y[11:0], x[11:0]}`, x чётный.
- **40 OSD_RECT:** w (2 байта), h (2 байта) BE, w чётная, затем пиксели построчно, байт = 2 пикселя, старший нибл левее. Байты сверх w/2·h отброшены. Кадр не длиннее буфера 8 КБ: большой прямоугольник идёт полосами.
- **41 OSD_FILL:** w, h, байт цвета (2 пикселя, можно узор). Заливка идёт после CS#↑, байт за такт 100 МГц: весь экран 1,5 мс. Пока она идёт, IRQ = 0 и STATUS бит 2 = 1; кадр 40 или 41 за это время отброшен целиком.
- **42 OSD_PAL:** по 3 байта R, G, B на цвет, индекс растёт с `addr[3:0]`. До первой записи палитра серая: индекс i = 17·i.
- **43 OSD_CTRL:** ключ `FBKY`, как у флеш-команд, иначе мусор на шине при перезагрузке супервизора прячет заставку.
- Пиксели за краем экрана отброшены. Смена палитры или CTRL посреди кадра портит не больше одного кадра.

Стенд, 10 МГц: FILL 640×480 1,6 мс, RECT 640×480 35 мс (4,3 МБ/с).

## Кнопки (PAD)
Супервизор опрашивает кнопки 1 кГц и шлёт PAD при каждой смене и повтором раз в 100 мс, только когда в ПЛИС профиль (ID `"FBPR"`). От смены кнопки до конца кадра PAD на стенде 115–129 мкс. Раскладка одинакова для всех ядер, как `cont1_key` Analogue Pocket. Ядро переводит её в свой контроллер само.

| Бит | Кнопка | Бит | Кнопка |
|---|---|---|---|
| 0 | Вверх | 8–13 | L1, R1, L2, R2, L3, R3 (на приборе нет) |
| 1 | Вниз | 14 | Select |
| 2 | Влево | 15 | Start |
| 3 | Вправо | | |
| 4 | A: правая кнопка ромба | 5 | B: нижняя |
| 6 | X: верхняя | 7 | Y: левая |

Кнопки прибора: крестовина → биты 0–3, F1 (верх) → X, F2 (право) → A, F3 (низ) → B, F4 (лево) → Y, Меню → Start, Назад → Select. Fn — модификатор: пока она нажата, игра кнопок не видит. Кнопки, нажатые вместе с Fn, остаются скрыты от игры до отпускания.

| Сочетание | Действие |
|---|---|
| Fn нажата и отпущена одна | меню поверх игры |
| Fn + Меню | сброс ядра |
| Fn + Назад | выход в golden (команда 22) |

NES (`gateware/profiles/nes/nes_pad.sv`): A → A, B → B, X → турбо A, Y → турбо B, турбо 10 Гц (3 кадра нажато, 3 отпущено). Противоположные направления вместе снимаются.

### Стенд: кнопки на ESP32-S3 DevKitC-1 N16R8
Кнопка замыкает ножку на GND, подтяжка внутри ESP. Все на гребёнке J3.

| J3 | GPIO | Кнопка | | J3 | GPIO | Кнопка |
|---|---|---|---|---|---|---|
| 4 | 1 | F2, право ромба | | 15 | 45 | Вниз |
| 5 | 2 | F1, верх | | 16 | 48 | Вправо |
| 6 | 42 | F4, лево | | 17 | 47 | Вверх |
| 7 | 41 | F3, низ | | 18 | 21 | Влево |
| 8 | 40 | Назад | | | | |
| 9 | 39 | Меню | | | | |
| 10 | 38 | Fn | | | | |

Нельзя: GPIO35–37 (J3-11…13) заняты octal PSRAM модуля R8 (даташит ESP32-S3-WROOM-1, с. 12, сноска b), кнопка на них ломает PSRAM и ESP уходит в перезагрузку. GPIO19/20 (J3-20/19) — USB консоли. GPIO0 (J3-14) — стрэп загрузки. GPIO45 — стрэп VDD_SPI: при сбросе нужен 0 (3,3 В), внутренняя подтяжка вниз это даёт, нажатая кнопка тоже.

ERASE, PROG, BOOT, TUNE и LA_ARM исполняются только при ровно 4 байтах данных `FBKY` в кадре (защита от мусора на шине, ошибка 5). Команды без данных исполняются, когда CS# поднимается. Флеш-команда, пришедшая, пока golden занят, даёт ошибку 3.

**Коды ошибок:** 0 нет, 1 защищённая область, 2 параметр, 3 занят, 4 неизвестная команда, 5 нет ключа.

**Двойная буферизация:** пока PROG пишет из одной половины буфера, ESP грузит следующие 4 КБ в другую через BUF_W и PARAM. Эти команды разрешены и в состоянии busy.

## ICAP и тулчейн
openXC7 (prjxray-db 2026-09) собирает ICAPE2, но в железе он не работает: регистры читаются 0, IPROG не действует. Проверено 7 вариантов: верхний и нижний сайт, перестановка бит, инверсия CSIB/RDWRB. Поэтому:
- **golden** собирается в Vivado: `make golden_vivado` в `gateware/`;
- **профили** собираются openXC7 или Vivado (`make viv_<цель>`). Из профиля openXC7 в меню можно вернуться только перезапуском питания модуля, профиль Vivado возвращается командой 22.
